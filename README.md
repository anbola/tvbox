## 二、为什么这次的直播会快

### 关键：用你自家运营商的源

直播流的速度**不取决于哪个源"名气大"，而取决于它是不是走你所在运营商的网**。

| 源类型 | 实际路径 | 实测码率 |
|---|---|---|
| 随便找的公共源（以前用的） | 你的移动宽带 → 跨网 → 山东联通/腾讯云服务器 | 大量失效，能通的也慢 |
| **中国移动陕西 IPTV 官方 CDN** | 你的移动宽带 → **同网同城节点** `39.134.x.x` | **20 000 – 48 000 kbps**，首字节 60–350ms |

所以本项目的直播源**全部换成** `dbiptv.sn.chinamobile.com`（中国移动陕西 IPTV 官方域名）。

### 实测数据（2026-10-31 晚，从你家这条宽带逐条探的）

```
候选 1500+ 条（跨 7 个社区源 + 移动 CDN 直连）
  → 逐条解析 PAT/PMT/SPS，确认「真能解 + 真高清」后入库 200+ 条
  → 按 1080p 优先、同网优先排序，每台保留 3 条线路

最终 88 个频道 / 154 条线路
  首条为 1080p（16:9）：55 个频道
  首条为 720x576 标清：33 个频道（基本都是只有标清源的本地台）
  有多条备用线路的频道：46 个
抽查首条线路 10 条：全部可播，首字节 0.2–1.3 秒
```

### 现在的内容

**88 个频道 / 154 条线路，主线路 100% 走移动 CDN**

- **央视** 24 个 —— CCTV-1 ~ 17 全部齐（上版缺的 CCTV-3 综艺、CCTV-5 体育、
  CCTV-6 电影、CCTV-8 电视剧这次补回来了），另含 CCTV-5+、CCTV老故事、CETV1-4、CGTN
- **卫视** 38 个（湖南/浙江/江苏/东方/北京/深圳/天津…）
- **陕西本地** —— 含 **商洛电视**、陕西新闻资讯/都市青春/影视/体育休闲/西部电影、
  西安 6 个频道、咸阳、渭南、延安、汉中、宝鸡、安康、榆林、铜川、杨凌
- 无台标外链（台标走境外图床会拖慢列表）

### 为什么央视显示成 4:3 方屏（以及怎么根治）

这是 2026-10-31 查清的一个真问题，跟播放器设置无关：

- 陕西移动 CDN 上大量央视频道是 **720×576**（PAL 标清）。这种流用的是**非正方形像素**，
  宽高比要靠码流里的 VUI/DAR 标记来说明"该铺成 16:9"。
- TVBox 的 **IJK 内核不读这个标记**，一律按"像素数之比"（720:576 ≈ 5:4）铺满，
  于是看到的就是被压扁的方屏。**播放器里设 16:9 是无效的**——那个开关作用在播放器
  的画面层，改不了解码器对源尺寸的判断。
- 唯一的根治办法：**给每个频道排一条真 1080p 的线路**（1920×1080 本身就是 16:9，
  任何内核都不会显示歪）。

所以 `lives/main.m3u` 的排序规则改成了「1080p > 720p > 576p」优先，
并且新增 `tools/live_expand.py` 专门去候选池里给还停在 576p 的频道找 1080p 备选。

### 多线路自动切换（不是靠运气）

TVBox 的 m3u 解析器（`TxtSubscribe.addChannel` → `mergeUrls`）**按频道名合并**：
同名的多条 `#EXTINF` 不会变成两个台，而是合并成「一个频道 + 多个 URL 列表」，
播放时按顺序试，前一条打不开就自动跳下一条。

所以本项目的做法是：每个频道保留 **3 条**，顺序为

1. 陕西移动自家 CDN 的 1080p
2. 其他线路的 1080p
3. 移动自家 CDN 的 576p（兜底，至少能看）

你在电视上不需要手动换源，正常换台就会用最优的那条。

## 三、点播：从 35 个采集站里实测选出的 4 个

### 筛选方法（不是靠推荐名单，是实测）

对 35 个公开采集站逐个测 4 项——分类树、首页列表、点开详情、**真实下载视频分片算码率**（每站采样 2 次取中位数）：

```
达标（视频 ≥1500kbps）仅 4 个：

站点    视频码率     首页耗时   详情耗时    片库
360     9 909 kbps   1 423 ms   867 ms    74 065
量子    5 086 kbps   2 110 ms   303 ms   161 888
暴风    3 069 kbps   2 207 ms  1 316 ms   169 894
非凡    1 538 kbps   1 839 ms   466 ms    98 881
```

被淘汰的典型：**豆瓣（视频超时）、金鹰（539kbps）、火狐（1 373kbps 不稳）、电影天堂（458kbps）、
百度（790）、天涯（324）、极速（840）**。你之前用的 5 个站里有 2 个是明显拖后腿的。

### 分类为什么不是「电影 / 电视剧」

实测这 4 个站的**「电影」主分类服务器端就是 0 条**（量子 1 条、暴风 14 条），「电视剧」也是 0–7 条。
片源全部放在子分类里。所以配置列的是**真有货的分类**，每站 14 个：

```
动作片 3860~5131   喜剧片 4060~7776   剧情片 13984~19885
科幻片 720~1350    爱情片 1003~3291   恐怖片 476~5140
国产剧 4553~9225   欧美剧 933~6708    香港剧 100~2967   韩国剧 332~1816
大陆综艺 1552~2937  动画片 500~974    国产动漫 2063~2711  纪录片 667~2797
```

（已剔除「伦理片 / 理论片」等成人分类——这是家里的电视。）

### 两个提速细节

- `quickSearch` 只给**最快的 2 个站**（360、量子）开启。搜索时 App 会并发查询所有开了 quickSearch 的站，
  站越多越慢——这是"搜索转圈"的常见原因。
- `filterable: 0`（不开筛选），`api` 用裸地址、**不写 `ext`**——这三条写错就会丢分类标签。

## 四、更新机制（你问的重点）

这里有个**必须知道的物理限制**：

> **测速只能在你自己家这条宽带上做。**
> GitHub 的自动任务跑在美国的服务器上，从那里测中国移动陕西的 IPTV，结果毫无意义
> （跨网 + 出国，必然是又慢又不通）。

所以流水线**拆成两段**，各干各擅长的事：

```
┌──────────────────────────── 云端（GitHub Actions）────────────────────────────┐
│ 每周六 21:30  tools/merge_pool.py                                             │
│   抓取 7 个社区源 → 去重 → 合并进 lives/pool.m3u（候选池）                      │
│   校验 tvbox_clean.json / main.m3u 结构 → 有问题就失败，不会把坏文件推上线        │
│   ⚠️ 不测速、不改 main.m3u、不改 tvbox_clean.json                              │
└───────────────────────────────────────────────────────────────────────────────┘
                                    ↓ 候选池
┌──────────────────────────── 本地（你的电脑）─────────────────────────────────┐
│ 双击  refresh.bat （或 python tools/refresh_all.py --deploy）                  │
│   ① fetch_sources  抓取候选源                                                 │
│   ② speedtest      逐条下载真实分片算码率（48 并发）                            │
│   ②.5 codec_probe  解析 PAT/PMT/SPS：视频编码 + 分辨率（HEVC 会崩、576p 是 4:3） │
│   ②.6 live_expand  给还停在 720x576 的频道补 1080p 备选线路                     │
│   ③ build_live     1080p 优先 + 同网优先 + 每台多条 → lives/main.m3u           │
│   ④ vod_probe      35 个采集站体检（API 延迟 + 视频分片速度）                    │
│   ⑤ build_config   只保留达标站 + 有货分类 → tvbox_clean.json                  │
│   ⑥ deploy_clean   推送到 GitHub → Pages 自动重建                             │
└───────────────────────────────────────────────────────────────────────────────┘
```

### 为什么更新改成每周六 21:30

原来是每天 04:00。那个点抓下来的候选池，要等到你晚上回家才有机会测速，
等于白等一整天；而你白天上班、只有晚上和周末在家，凌晨那次更新对你没有任何可见收益。

现在改成**每周六 21:30**：周末你在家、全网也最闲，抓完顺手跑一次 `refresh.bat` 就行，
周中不再打扰。候选池本来就是"只增不减"的，一周补一次完全够用。

### 什么时候需要跑一次本地刷新

| 情况 | 做法 |
|---|---|
| 直播个别台失效 | 双击 `refresh.bat`（全流程约 3–5 分钟） |
| 点播某个站变慢/挂了 | 双击 `refresh.bat`，它会自动换掉慢站 |
| 想设成自动 | Windows「任务计划程序」→ 每周一次 → 程序填 `refresh.bat` 的完整路径 |
| 只想更新直播 | `python tools/refresh_all.py --no-vod --deploy` |
| 没网/懒得多跑 | 至少每周手动跑一次，源会自然老化 |

`refresh.bat` 默认带 `--deploy`，会自动推 GitHub。令牌放在项目根目录的 `anbola_token.txt`
（已在 `.gitignore` 里，不会进仓库）。

## 六、排错

**Q1. 提示「配置解析失败」**
配置只保留 `sites` + `lives` 两个键，没有任何外链依赖，正常不会报这个错。若仍出现：
确认「直播源」框是空的；确认 App 里没有残留旧地址；清一下 App 的配置缓存再重新导入。

**Q2. 直播有台名但打不开**
每个频道只有 1–3 条流，移动源单条失效时没有备用。解决方法：跑一次 `refresh.bat` 重新体检。

**Q3. 点播首页一片空白，什么都没有**
先确认能看到上方的分类标签（动作片/喜剧片/剧情片…），**点一下标签**就有内容了。
原因是采集站的「电影」主分类服务器端就是 0 条（实测 360=0、非凡=0、量子=1、暴风=14），
而播放器默认打开的是第一个分类。这是片源站的特性，不是配置错。
若连分类标签都没有，说明配置没加载成功：清 App 缓存 → 重新填一次地址 → 重载。

**Q4. 点直播闪一下就退回首页**

v2.2 已定位并修好，根因跟分辨率、码率都无关：

```
E/OMXNodeInstance: getParameter(OMX_IndexParamAudioMp3) ERROR 0x8000101a
F/ACodec: CHECK_EQ(mOMX->getParameter(...AudioMp3...)) failed
F/libc  : Fatal signal 6 (SIGABRT) in tid MediaCodec_loop
```

这些移动源的**音频是 MP3**，而这台电视（微鲸 WTV55K1 / Android 5.0.2 / MStar）的 OMX 组件
不支持 `OMX_IndexParamAudioMp3` 查询，Android 的 ACodec 里那句 `CHECK_EQ` 失败会直接
`abort()` 掉整个进程。**EXO 硬解 + MP3 音频 = 必崩。**

修法（已写进配置，无需手动设）：`lives` 里固定 `playerType` 为 `1`，让直播走 IJK 软解。
点播仍然走 EXO 硬解，速度不受影响。

如果换了别的设备/客户端又想手动确认：设置 → 播放器 → **IJK播放器**；
设置 → IJK解码方式 → **软解码**。

**Q5. 点播打开慢**
首页列表本身要 1.4–2.2 秒（这是采集站的服务器速度，改不了）。能改的是：
- 只留 4 个站（已做）
- quickSearch 只开 2 个（已做）
- **换播放器**：老版 TVBox 在海信/创维等电视上解码弱，换成 **FongMi（蜂蜜影视）** 或 **影视仓**，
  同样的源会明显更顺。TVBox 原版留作备用即可。

**Q6. 直播能播但偶有卡顿**
移动 IPTV 单播源走的是运营商内网 CDN，晚高峰（20:00–22:00）会有波动。可在播放页长按切下一条。
